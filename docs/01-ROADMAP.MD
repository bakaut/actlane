# Actlane Roadmap and Acceptance Criteria

## Purpose

This roadmap exists to prevent Actlane from becoming too broad too early.

Actlane should start as a small, testable idea:

```text
one capability contract
→ generated agent/runtime artifacts
→ reproducible lockfile
→ safe brownfield adoption
```

The goal is not to build an enterprise platform first.
The goal is to validate whether developers and teams need portable, policy-aware capability packs for AI agents.

---

## Product Thesis

AI-agent actions are currently scattered across prompts, skills, MCP schemas, OpenAPI Actions, IDE configs, gateway rules, and human memory.

Actlane provides a source of truth:

```text
actlane.yaml = desired capability contract
actlane.lock = exact generated/applied state
```

From that source of truth, Actlane can generate:

```text
AGENTS.md
SKILL.md
MCP metadata
OpenAPI Actions
IDE/agent config snippets
policy bundles
contract tests
audit metadata
```

Optional runtime enforcement may come later.

---

# Phase 0 — Public RFC / Demand Validation

## Goal

Validate the problem before writing real implementation code.

## Scope

Create a public repository with:

```text
README.md
MANIFESTO.md
ROADMAP.md
spec/v1alpha1/
packs/safe-gitops/
examples/create-safe-draft-pr/
diagrams/
website/articles/
```

The repository is explicitly a design/specification repository, not a working tool yet.

## Acceptance Criteria

Phase 0 is complete when:

```text
- README explains the pain in under 30 seconds.
- Manifesto clearly states what Actlane is and is not.
- One concrete pack exists: safe-gitops.
- One concrete workflow exists: create-safe-draft-pr.
- Example generated artifacts exist, even if hand-written.
- STATUS.md says: pre-alpha / RFC / no production CLI yet.
- Call to action is clear: star, open issue, request target/runtime.
```

## Demand Signals

Track:

```text
- GitHub stars
- issues opened
- discussions/comments
- requests for specific targets: OpenCode, Codex, VS Code, Custom GPT, Orchestra
- SEO impressions/clicks
- people asking “when CLI?”
```

## Expand Criteria

Move to Phase 1 if at least 2 of these are true:

```text
- 10+ stars from relevant developers
- 3+ meaningful issues or discussions
- 2+ people ask for a working CLI
- 1+ person wants to try it on a real repo
- SEO pages receive early impressions/clicks
```

## Kill or Pause Criteria

Pause or reframe if:

```text
- people do not understand the problem after reading README
- nobody opens examples
- feedback is mostly “why not just MCP?”
- nobody asks for generated artifacts or CLI
```

# Phase 1 — Minimal CLI Prototype

## Goal

Make Actlane real enough to run locally.

## Scope

Implement only the smallest useful CLI:

```bash
actlane validate
actlane generate --target mcp
actlane generate --target agents
actlane generate --target policy
```

No runtime enforcement yet.
No gateway.
No registry.
No SaaS.

## Required Inputs

```text
actlane.yaml
capabilities/*.yaml
policies/*.yaml
target-profile.yaml
```

## Required Outputs

```text
generated/AGENTS.md
generated/skills/create-safe-draft-pr/SKILL.md
generated/mcp/create-safe-draft-pr.tool.json
generated/policies/policy-bundle.json
actlane.lock
```

## Acceptance Criteria

Phase 1 is complete when:

```text
- CLI validates the safe-gitops pack.
- CLI fails clearly on invalid schema.
- CLI generates at least AGENTS.md, SKILL.md, MCP metadata, and policy bundle.
- Generated files are deterministic.
- actlane.lock is created.
- actlane generate --frozen-lockfile works.
- Example pack can be generated from a clean checkout.
- No existing user files are modified.
```

## Non-Goals

```text
- no apply command
- no runtime check
- no webhook
- no gateway plugin
- no marketplace
- no enterprise UI
```

# Phase 2 — Brownfield-Safe Adoption

## Goal

Allow users to try Actlane inside an existing project without fear.

## Scope

Add safe project adoption lifecycle:

```bash
actlane inspect
actlane init --no-touch
actlane generate
actlane diff
actlane plan apply
actlane remove --dry-run
```

## Acceptance Criteria

Phase 2 is complete when:

```text
- inspect detects existing AGENTS.md, SKILL.md, MCP configs, OpenCode config, VS Code config where possible.
- init --no-touch creates only .actlane/ files.
- generate writes only to .actlane/generated by default.
- diff shows what would change before apply.
- no existing file is modified without explicit apply.
- generated snippets are clearly marked.
- ownership metadata is recorded in actlane.lock.
- remove --dry-run shows exactly what would be removed.
- remove deletes only Actlane-owned files or Actlane-owned blocks.
```

## Expand Criteria

Move to Phase 3 if:

```text
- at least one user tries Actlane in an existing repo
- generated artifacts are useful without manual rewriting
- remove behavior is trusted
```

# Phase 3 — More Targets, Still Generation-First

## Goal

Prove that Actlane is useful across multiple agent runtimes.

## Scope

Add target adapters gradually.

Priority order:

```text
1. AGENTS.md
2. SKILL.md
3. MCP metadata
4. OpenCode snippets
5. VS Code MCP config snippets
6. OpenAPI Actions for Custom GPT
7. Codex/Cursor/Cline/Continue snippets
8. Orchestra pack target
```

## Acceptance Criteria

Phase 3 is complete when:

```text
- at least 3 targets are generated from the same actlane.yaml.
- each generated target has a test fixture.
- target output is deterministic.
- target docs explain where the generated artifact should be copied or applied.
- target-specific quirks are isolated in adapters, not in core DSL.
```

## Guardrail

Do not add a new target unless:

```text
- at least one user asks for it, or
- it is needed for the safe-gitops demo, or
- it materially improves portability.
```

# Phase 4 — Local Policy Check

## Goal

Introduce optional policy evaluation without becoming a gateway.

## Scope

Add:

```bash
actlane check tool-call.json --policy generated/policies/policy-bundle.json
```

Supported decisions:

```text
allow
deny
mutate
requires-approval
```

## Acceptance Criteria

Phase 4 is complete when:

```text
- check can validate allow and deny examples.
- check can apply safe default mutations such as branch prefix, draft=true, timeout.
- check outputs before/after mutation diff.
- check produces a machine-readable decision JSON.
- check never silently changes semantic intent.
- denied calls include clear human-readable reason.
```

## Non-Goals

```text
- no long-running service
- no sidecar
- no gateway integration
- no enterprise approval workflow
```

---

# Phase 5 — Optional Runtime Enforcement

## Goal

Allow teams to enforce Actlane policy at runtime if they want to.

## Scope

Add one optional runtime mode only after local policy check is stable.

Possible modes:

```text
1. local MCP wrapper
2. webhook/PDP service
3. gateway integration bundle
```

Preferred first runtime:

```text
local MCP wrapper for development and demos
```

## Acceptance Criteria

Phase 5 is complete when:

```text
- runtime mode is optional.
- generation mode still works without daemon/service.
- runtime uses the same policy bundle generated from actlane.yaml.
- runtime logs decision, original input, mutated input, and result.
- fail mode is explicit: deny or allow.
- latency and failure behavior are documented.
```

## Guardrail

Actlane must not be positioned as an MCP gateway.

Correct message:

```text
Bring your own gateway.
Use Actlane as the capability contract and policy source of truth.
```

# Phase 6 — Private Pack Distribution

## Goal

Make Actlane useful for sharing private capability packs between developers and teams.

## Scope

Add pack lifecycle:

```bash
actlane pack create
actlane pack inspect
actlane pack install
actlane pack remove
actlane pack verify
```

Pack format:

```text
actlane.yaml
AGENTS.md
skills/
policies/
mcp/
adapters/
examples/
actlane.lock
checksums.txt
```

## Acceptance Criteria

Phase 6 is complete when:

```text
- a pack can be zipped and shared privately.
- another developer can inspect the pack before installing.
- checksums are verified.
- installed files are tracked in actlane.lock.
- pack removal is safe and predictable.
- pack can be adapted to at least two agent runtimes.
```

## Non-Goals

```text
- no public marketplace
- no hosted registry
- no paid SaaS
```

---

# Phase 7 — Ecosystem and Enterprise Options

## Goal

Only after real usage, explore broader distribution and commercial layers.

## Possible Extensions

```text
hosted/private registry
signed packs
RBAC/SSO
audit dashboard
approval workflow
enterprise policy packs
MCP gateway integrations
Orchestra/OpenCode marketplace packs
JFrog/internal artifact registry support
```

## Acceptance Criteria

Do not start Phase 7 unless:

```text
- multiple teams or users want to share packs
- private pack distribution is used manually
- users ask for governance, signatures, or audit reports
- there is evidence that a paid/control-plane layer solves a real operational problem
```

# Product Guardrails

## Always True

```text
DSL-first.
Generation-first.
Runtime optional.
Gateway optional.
Private packs first.
No silent project modification.
No generated artifact without reproducibility.
```

## Never in Early Phases

```text
No marketplace-first strategy.
No SaaS-first strategy.
No full workflow language in YAML.
No replacing MCP.
No replacing agent frameworks.
No claiming production security before runtime exists.
```

---

# Minimal Viable Proof

The smallest proof that Actlane is useful:

```text
one safe-gitops pack
one create-safe-draft-pr capability
one actlane.yaml
one actlane.lock
three generated outputs:
  AGENTS.md
  SKILL.md
  MCP tool metadata
one policy bundle
one allow/deny/mutate example
```

If this does not feel useful, do not expand.
